Content Refresh Prioritization

Abstract

This project asks how an editorial team can rank existing content pages for refresh review when review capacity is limited. The anonymized starter release contains 30,000 content items across 32 pseudonymized clients. A transparent rule baseline is compared with supervised models using a client-aware holdout and Precision@50. The bundled reference run measured 0.240 Precision@50 for the baseline and about 0.740 for the random forest, against a 0.542 label base rate. The output is decision-support for human review, not causal evidence that refreshing a page will improve traffic.

Problem

Editors need an ordered review queue rather than an undifferentiated list. False positives cost review time; false negatives can leave useful review opportunities unattended.

Data

The public-safe release uses pseudonymized content items and aggregated activity. Label-derived trend fields, IDs, product flags, private identifiers and unsafe future windows are excluded from model features.

Methodology

The target is trend_direction == down. The baseline combines visibility, freshness, position and content-depth signals. Logistic regression, a decision tree and a random forest provide learned ranking scores. Client-aware validation is preferred to avoid sharing client-specific patterns between train and test.

Limitations

The label is a snapshot-derived trend indicator, not a treatment outcome. The panel is unbalanced, some history is source-limited, and recent windows can overlap depending on release. Model importance is not causality, and the system does not predict Google's algorithm.

Ranked recommendations

  1. Inspect high-confidence pages with multiple supporting reason codes.
  2. Review CTR/search-intent alignment for visible low-CTR pages.
  3. Inspect completeness before expanding thin content.
  4. Review engagement and page experience for engagement candidates.
  5. Monitor lower-confidence items until new evidence changes their priority.

Reproducibility

Run scripts 01 through 04 in order from the repository root. The modeling seed is 42. The full analysis is documented in work/notebooks/.
